## 1. 대상 기업

**OT전자**(가상 기업)는 데이터센터 냉각 인프라를 공급하는 전문 기업입니다.

| | |
| --- | --- |
| 냉각설비 공급 | 칠러 · CDU · 열교환기 등 핵심 장비 |
| 현장 구축 | 배관 · 펌프 · 제어 설계, 설치 및 시운전 |
| 운영 지원 | 예방정비, 장애 복구, 증설 및 성능 개선 |

사업이 한 번의 판매로 끝나지 않고, 고객과 장비의 기록이 수년 동안 이어진다는 점이 이 도메인의 특징입니다.

```
SELL              DELIVER            OPERATE           GROW
고객 요구·기술검토   변경·설치·시운전     예방정비·장애·복구   갱신·증설·다음 수주
계약               인수
──────────────    ──────────────    ──────────────    ──────────────
Account           Project           Case              Opportunity
Opportunity       Asset             Work Order        Knowledge
```

Salesforce의 역할은 설계·제어 같은 전문 시스템을 대체하는 것이 아니라, **고객 · 프로젝트 · 실제 장비를 기준으로 결과를 연결하는 것**으로 정의했습니다.

## 2. AS-IS — 시간은 어디에 쓰이고 있었나

데모 시나리오의 장애 한 건(CDU-A-07, 유량 저하)을 시간 단위로 분해했습니다.

```
14:14 최초 접수 ─────────────────────────────────────────── 21:05 복구 확인

┌──────────────────────────┬────────┬──────────────┬────────┐
│  접수 · 맥락 재구성        │ 현장 이동 │ 현장 점검·수리  │ 안정화  │
│      3시간 12분           │  45분   │    2시간      │  54분  │
└──────────────────────────┴────────┴──────────────┴────────┘
   └─ 개선 가능 구간 ─┘

고객이 체감한 복구 시간   6시간 51분
실제 복구 작업             2시간
```

**접수 · 맥락 재구성 3시간 12분**은 다음 과정에 쓰였습니다.

```
장비 특정 → 계약 · 보증 확인 → 도면 · 변경 이력 확인 → 과거 기록 대조
```

### 왜 이 시간이 필요했나

같은 장비를 보는 다섯 역할이 각자 필요한 맥락을 처음부터 다시 만들고 있었습니다.

| 역할 | 담당 | 매번 다시 찾던 것 |
| --- | --- | --- |
| 고객 | 시설 담당자 | 어느 장비인가 |
| 서비스 | 상담 · 배정 | 보증과 SLA는 어떻게 되나 |
| 설계 | 사양 · 도면 | 적용된 Revision은 무엇인가 |
| 현장 | 점검 · 조치 | 과거 변경 위치는 어디인가 |
| 영업 | 갱신 · 제안 | 다음 제안의 근거는 무엇인가 |

**핵심 문제 — 앞 단계의 기록이 다음 사람의 판단과 행동에 바로 사용되지 않았습니다.**

---

## 3. TO-BE — 맥락을 이어받는다

모든 정보를 한곳에 모으는 것이 아니라, **판단에 필요한 기록을 업무 순간에 연결**하는 방향을 택했습니다.
같은 장비를 보는 다섯 역할이 앞 단계에서 남은 기록으로 다음 업무를 시작합니다.

| 역할 | 이어받는 맥락 |
| --- | --- |
| 고객 | 장비 · 증상 · 고객 요구 |
| 서비스 | 계약 · 보증 · SLA · 유사 사례 |
| 설계 | 승인 Revision · 설계 · 변경 이력 |
| 현장 | 변경 위치 · 점검 · 조치안 |
| 영업 | RCA · 예방 조치 · 다음 제안 |

이 연결은 **장비별 Case를 축으로** 이루어집니다. 하나의 Case가 고객 · 서비스 · 현장 · 영업을 거치며 업무 이력이 끊기지 않고 이어집니다.

## 4. AI의 역할과 경계

Agentforce는 네 단계에서 판단 근거를 정리합니다. **결정과 승인은 사람이 합니다.**

| 단계 | Agent가 하는 일 |
| --- | --- |
| 고객 응대 | MIAW 상담 · Knowledge 검색 · 증상 구조화 · Case 생성 |
| 출동 브리핑 | 12대 기록 비교 · 유사 사례 탐색 · 복수 가설 · 점검 순서 준비 |
| 전문가 연결 | Slack Swarming 채널 생성 · Asset Type Expert Finder |
| 결과 요약 | 완료 보고를 Case에 반영 · 증설 제안 초안 준비 |

실행 조건은 다음과 같이 설계했습니다.

```
AGENT  후보 · 근거 준비
  ↓
HUMAN  판단 · 승인
  ↓
FLOW   후속 업무 발행
  ↓
RULE   미승인 상태 차단
```

**AI가 판단을 대신하지 않도록, 역할과 실행 조건을 함께 설계했습니다.**

### 프롬프트 설계 원칙

브리핑은 사람의 판단을 **돕는** 자리입니다. 틀린 값이 하나 섞이면 도움이 아니라 방해가 되므로, 무엇을 하게 할지보다 **무엇을 하지 못하게 할지**를 먼저 정했습니다.

| 규칙 | 이유 |
| --- | --- |
| 이력에 없는 값 · 날짜 · 부품명을 지어내지 마라 | 현장에서 확인할 근거가 없는 문장은 판단을 방해합니다 |
| 값이 비어 있는 항목은 미측정이지 이상이 아니다 | 측정하지 않은 것과 측정했는데 벗어난 것은 다른 상태입니다 |
| 표본이 3건 미만이면 참고용이라고 명시하라 | 적은 표본으로 경향을 말하면 우연을 원인으로 읽게 됩니다 |
| 판정과 추세를 섞어 쓰지 마라 | 판정은 사양 대비 합격 여부, 추세는 기준선 대비 변화입니다 |
| 원문을 그대로 나열하지 마라 | 건수만큼 항목이 나왔다면 묶기에 실패한 것입니다 |

출력물의 마지막 줄에는 항상 다음 문장이 포함됩니다.

> 이 결과는 제시이며 진단 확정이 아니다. 최종 소견은 담당 엔지니어가 기록한다.
