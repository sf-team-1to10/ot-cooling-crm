# CI/CD 운영 기준

[← README](../README.md)

이 문서는 OT Cooling CRM에서 실제로 구현 · 검증한 GitHub Actions 기반 PR 검증 흐름을 기준으로 작성했습니다.
PR을 검토하거나 배포 자동화를 논의할 때, **어디까지 자동화되어 있고 무엇을 사람의 판단으로 남겨 두었는지**를 확인하는 용도입니다.

---

## 1. 현재 상태 — 수동 승인형 CI, CD 미구축

`main` 대상 PR에서 Salesforce 메타데이터가 바뀌면 GitHub Actions가 통합 Sandbox(T0INT)에서 배포 가능 여부와 전체 Apex 테스트를 자동으로 확인합니다.
**병합은 사람이 결과를 보고 직접 수행**하며, `main` 병합 후 자동 배포하는 CD는 구성하지 않았습니다.

```
기능 브랜치 작업
      ↓
main 대상 PR 생성 또는 기존 PR에 새 커밋 push
      ↓
GitHub Actions 자동 검증
      ↓
T0INT 배포 가능 여부 + 전체 Apex 테스트 확인
      ↓
결과 확인 후 수동 병합
      ↓
T0INT 반영은 별도 수동 배포
```

---

## 2. PR 검증 흐름

워크플로 파일: `.github/workflows/pr-develop-branch.yml`

`main` 대상 PR이 열리거나(`opened`) 같은 브랜치에 새 커밋이 push될 때(`synchronize`) 실행되며, `force-app` 아래 파일이 바뀐 PR만 검사합니다.

| 단계 | 수행 내용 | 의미 |
| --- | --- | --- |
| 소스 가져오기 | PR의 변경 내용을 임시 환경에 가져온다 | PR 최신 상태를 기준으로 검사 |
| delta 생성 | `main`과 PR을 비교해 추가 · 수정 · 삭제된 메타데이터만 추린다 | 전체가 아니라 이번 변경분만 검사 |
| T0INT 인증 | `SFDX_INTEGRATION_URL` Secret으로 접속 | 인증 정보는 yml · PR · 로그에 넣지 않는다 |
| 배포 가능 여부 검사 | delta 변경분을 실제 반영 없이 검사 (`--dry-run`) | 배포 시 오류가 나는지 미리 확인 |
| 전체 Apex 테스트 | `RunLocalTests` 실행 | 변경이 기존 로직을 깨지 않는지 확인 |
| 삭제 변경 검사 | 삭제 메타데이터를 실제 삭제 없이 검증 | 삭제 작업의 오류를 미리 확인 |

> Actions가 통과해도 `--dry-run`이므로 **T0INT에 실제로 배포되지는 않습니다.**

### 팀 사용 방법

1. 작업 브랜치에서 Salesforce 메타데이터를 수정한다
2. `main` 대상 PR을 생성한다
3. PR의 **Checks** 탭에서 `validate-deployment-on-develop-org` 결과를 확인한다
4. 수정이 필요하면 같은 브랜치에 commit · push한다 — 새 PR 없이 검사가 자동 재실행된다
5. 통과한 PR만 병합한다

PR 본문에 테스트 지시문을 적을 필요는 없습니다. **모든 대상 PR에서 전체 Apex 테스트를 자동 실행**합니다.

### 필수 Secret

| Secret | 용도 | 주의 |
| --- | --- | --- |
| `SFDX_INTEGRATION_URL` | GitHub Actions의 T0INT 인증 | SFDX Auth URL 전체를 저장. 코드 · PR · 채팅 · 스크린샷에 공유하지 않는다 |

## 3. 의사결정 배경

### PR 본문 명령 대신 전체 Apex 테스트 자동 실행

처음 구성은 PR 본문에서 특정 Apex 테스트를 지정하는 방식이었습니다. 프로젝트에서 Apex 비중이 높지 않고, 팀원이 매 PR마다 문법을 기억해 입력하면 누락 · 형식 오류가 생길 수 있어 **전체 실행으로 단순화**했습니다.

검사 시간을 조금 줄이는 것보다, 팀이 같은 방식으로 빠뜨리지 않고 검사받는 것이 현재 단계에서 더 중요하다고 판단했습니다.
Apex 테스트가 늘어 PR 시간이 실제 부담이 되면 다시 검토합니다.

### 검증 자동화와 배포 자동화를 분리

Actions는 T0INT에 실제 반영하지 않는 check-only 검사입니다.
여러 작업이 동시에 진행되는 상황에서 PR 하나가 열렸다고 공유 통합 환경을 자동 변경하지 않기 위한 선택입니다.

Salesforce 작업은 필드 · Layout · Flow · 표준 선택값 · 권한 · Setup UI 변경처럼 의존성이 많습니다. 작업 순서와 반영 책임이 정리되지 않은 상태에서 자동 배포를 열면, 한 PR의 자동 반영이 다른 작업자의 검증 환경을 바꿀 수 있습니다.

### PR 검증은 현재 T0INT 상태를 기준으로 한다

Actions는 다른 열린 PR의 변경사항을 미리 합쳐서 검사하지 않습니다. 검사 시점의 실제 org를 기준으로 해당 PR의 delta만 봅니다.

PR A가 새 필드를 만들고 PR B가 그 필드를 Layout에 배치할 때, A가 반영되지 않은 상태에서 B는 실패할 수 있습니다.
이는 오류라기보다 **B가 A에 의존한다는 사실을 드러내는 정상적인 결과**입니다. PR 순서와 통합 배포 순서를 관리할 때 중요한 기준입니다.

### GitHub 환경 제약

- **SARIF 업로드 제외** — Apex Scanner 결과를 GitHub Security에 올리려면 Advanced Security가 필요합니다. 배포 검사와 테스트는 업로드 없이도 동작하므로 현재는 제외했습니다.
- **Ruleset 미적용** — Free 조직의 비공개 저장소에서는 Ruleset이 적용되지 않아, 실패한 Actions를 GitHub가 기술적으로 병합 차단할 수 없습니다. 현재는 **통과한 PR만 병합**하는 운영 원칙으로 대신합니다.

## 4. 운영 기준

| 상황 | 권장 행동 |
| --- | --- |
| 일반 Salesforce 변경 PR | `main` 대상 PR 생성 → Actions 통과 확인 → 수동 병합 |
| 기존에 열려 있던 PR | 새 커밋을 한 번 push해 Actions 재실행 |
| 앞 작업의 필드 · Flow · Layout을 참조하는 PR | 선행 작업의 org 반영 여부를 먼저 확인하거나 의존 PR을 순서대로 검증 |
| Actions 실패 | 병합하지 않고 실패 단계의 오류 원인 확인 |
| `main`에는 있지만 org에 없는 변경 | 새 PR에서 의존성 오류가 날 수 있으므로 org 반영 상태를 별도 관리 |
| Setup UI로만 변경한 표준 선택값 | Git 소스만으로 재현되지 않으므로 org 설정 반영 여부를 별도 확인 |

---

## 5. CD를 도입하려면

프로젝트 중 `production` 브랜치를 운영 org와 1:1로 맞추고 **병합이 곧 배포**가 되도록 구성한 적이 있습니다.

문제는 다음 경로에서 발생했습니다.

```
PR 생성 · 검증 시작 ──> 검증 통과 대기 ──> 병합 = 운영 배포 ──> 최신 작업이 덮인다
                            │
                            └── 그 사이 다른 작업자가 운영 org에서 직접 작업
```

PR이 검증을 통과하는 동안 다른 작업자가 운영 org에서 직접 변경합니다. 그 사이 병합이 일어나면 **Git에 있는 이전 상태가 org의 최신 작업을 덮어씁니다.**
배포는 성공하고, 사라진 작업은 드러나지 않습니다.

Salesforce는 코드만으로 상태가 정해지지 않습니다. Setup 화면에서 직접 바꾼 설정은 Git에 남지 않고, 그 차이가 자동 배포와 만나면 최신 작업이 조용히 사라집니다.
**자동화보다 먼저 갖춰져야 하는 것은 서버와 브랜치의 동기화**입니다.

### 도입 전 확인할 조건

1. `main`의 소스가 org 상태와 지속적으로 일치해야 한다
2. 필드 · Layout · Flow 등 작업 간 의존성이 PR 순서와 배포 순서로 관리되어야 한다
3. Setup UI에서만 변경하는 표준 선택값 · 승인 설정 등의 반영 방식을 정해야 한다
4. 삭제 변경의 승인 · 검증 · 롤백 기준을 정해야 한다
5. 통합 org 자동 배포 이후 Staging · Production으로 가는 환경별 책임과 승인 기준을 정해야 한다
6. 필수 상태 검사와 PR 보호 규칙을 적용할 수 있는 GitHub 환경을 준비해야 한다

이 조건이 정리되기 전까지는 **PR 자동 검증 + 수동 병합 + 통합 환경 수동 배포**가 더 안전한 운영 방식입니다.
